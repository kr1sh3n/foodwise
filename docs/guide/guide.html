What it is: a web app that connects campus food providers (cafeterias, hostel messes, restaurants) with students and NGOs, so that leftover food is collected and eaten instead of thrown away – and every rescued meal is counted.

Functions of the app

1. Role-based accounts

  • Sign up as Provider, Student or NGO; each gets its own dashboard.
  • Secure login (JWT); each role can only do its own actions.

2. Food listings (providers)

  • Photo, name, category, veg/non-veg, quantity, pickup spot, prepared time and a “collect by” deadline.
  • Edit or withdraw a listing at any time.

3. Discover food

  • Search by name; filter by category and diet; sort by ending soonest, newest or largest.
  • Cards show quantity left and time left.

4. Requests & approval

  • Students request up to 3 servings, NGOs in bulk.
  • Approval reserves stock instantly – food can never be promised twice.

5. Verified pickup

  • Approved users get a 4-digit pickup code.
  • Provider enters the code at the counter; only then is the food counted as rescued.

6. Auto-expiry & notifications

  • Listings past their deadline expire automatically (checked every minute).
  • Bell alerts for approvals, rejections, cancellations and 1-hour reminders.

7. Impact dashboard

  • Meals rescued, kg saved, CO₂ avoided, pickups, vendors.
  • Weekly charts, category split; campus-wide or “just me”.

8. Leaderboard

  • Top providers and top rescuers by week, month or all time.
  • Points = 10 per kg rescued + 5 per pickup.
How to use it

As a Provider (canteen / mess / restaurant)

  1. Sign up → choose Food Provider → enter canteen name.
  2. Click List food, add details and deadline → Publish.
  3. On the dashboard, Approve or Decline incoming requests.
  4. When someone arrives, click Confirm pickup and type their 4-digit code.

As a Student / NGO

  1. Sign up → choose Student or NGO.
  2. Open Discover, search or filter, and open a food card.
  3. Choose quantity → Send request; wait for the bell notification.
  4. Go to the pickup spot before the deadline and show your pickup code.

FoodWise is a full-stack web application with three parts: a frontend (what the user sees, running in the browser), a backend (a server that holds the rules and talks to the database) and a database (where all data is stored permanently). They talk to each other through a REST API using JSON.

2. Steps followed to build it

  1. Requirements: listed the users (provider, student, NGO), features, and rules (e.g. a student can take at most 3 servings).
  2. Database design: four tables and their relations written in server/prisma/schema.prisma.
  3. Backend API: Express routes for auth, listings, requests, notifications, impact, leaderboard and uploads, with login/role middleware and Zod validation.
  4. Business logic: safe stock reservation, request states, pickup codes, auto-expiry job and impact calculations.
  5. Frontend: React pages (Landing, Login/Register, Discover, Food details, Dashboards, List food, Impact, Leaderboard, Notifications) connected to the API.
  6. Demo data: a seed script creates 14 users, ~90 listings and ~350 requests covering 8 weeks, so charts and leaderboards look realistic.
  7. Testing: every flow was tested in the browser and through the API (wrong pickup code, over-limit requests, role restrictions, expiry, mobile layout), and bugs found were fixed.

5. How a request flows through the system

  1. Student clicks Send request → frontend sends POST /api/requests with the JWT token.
  2. Backend checks the token (logged in?), the role (student/NGO?), the input (Zod), the student limit (≤ 3) and that enough food remains → saves a PENDING request with a random 4-digit code.
  3. Provider clicks Approve → inside a database transaction the stock is reduced only if enough is left, the request becomes APPROVED, and a notification with the code is created.
  4. At pickup the provider enters the code → if it matches, the request becomes COLLECTED; when all food is collected the listing becomes COMPLETED.
  5. The impact page adds up all COLLECTED requests to show meals, kg and CO₂.

6. Key code: safe stock reservation

This is the most important piece of logic. Two approvals could happen at the same moment (two staff members, or a double click); the check and the subtraction happen in one atomic database step, so the remaining quantity can never go below zero.

// server/src/routes/requests.ts – approve a request
await prisma.$transaction(async (tx) => {
  // Only subtracts if enough is left (remaining >= requested quantity)
  const dec = await tx.foodListing.updateMany({
    where: { id: fr.listingId, remaining: { gte: fr.quantity } },
    data:  { remaining: { decrement: fr.quantity } },
  });
  if (dec.count === 0) throw bad('Not enough quantity left to approve this request');
  await tx.foodRequest.update({ where: { id: fr.id }, data: { status: 'APPROVED' } });
  // ...notify the requester, auto-decline pending requests that no longer fit
});

10. Security measures

  • Passwords hashed with bcrypt (salted, cost factor 10) – the real password is never stored.
  • Every protected request needs a valid JWT; wrong or expired token → 401 Unauthorized.
  • Role-based access control on the server: e.g. only providers can approve; a provider can only manage their own listings → 403 Forbidden otherwise.
  • All input validated with Zod; uploads limited to images under 5 MB.
  • Prisma uses parameterised queries, which protects against SQL injection.
  • Pickup codes ensure food goes to the approved person only.

11. Limitations and future scope

  • Now: prototype with demo data; in-app notifications only; no admin/moderator role; no automated test suite.
  • Future: college single sign-on, SMS/e-mail/push alerts, map navigation to pickup points, AI demand prediction so kitchens cook the right amount, food-safety checklist, mobile app, admin panel, cloud deployment.

Viva Questions & Answers

A. Project basics
1.What is your project?
FoodWise is a web app that connects campus food providers – cafeterias, hostel messes and restaurants – with students and NGOs, so that surplus food is redistributed instead of wasted. It also measures the impact in meals, kilograms and CO₂ saved.
2.What problem does it solve?
Campus kitchens cook in bulk for uncertain demand, so edible food is often thrown away at the end of the day. Sharing it through WhatsApp groups is informal: quantities aren’t tracked, many people come for the same food, and nothing is recorded. FoodWise gives a structured, real-time and trackable channel.
3.Who are the users?
Three roles: Providers (list food, approve requests, verify pickups), Students (request up to 3 servings) and NGOs (request bulk quantities for shelters and community kitchens).
4.How is it different from apps like Zomato or OLIO?
Zomato sells food; FoodWise is free redistribution. OLIO is open to the general public. FoodWise is built for a campus: it has institutional roles, provider approval, stock reservation, pickup codes, automatic expiry and campus-level impact reporting.
5.What are the main modules?
(1) Authentication & roles, (2) Food listings & expiry, (3) Discovery & search, (4) Requests & pickup, (5) Notifications, impact & leaderboard.
6.Explain the complete flow of the app.
Provider lists food → student/NGO finds it on Discover and requests a quantity → provider approves (stock reserved) → requester gets a notification with a 4-digit code → at pickup the provider enters the code → request becomes collected → impact and leaderboard update. Listings past their deadline expire automatically.
B. Frontend
7.Which technologies did you use for the frontend?
React 19 with TypeScript, Tailwind CSS for styling, React Router for pages, Recharts for charts, Framer Motion for animations, Lucide for icons, and Vite as the build tool.
8.Why React?
React builds the UI from reusable components and automatically re-renders when data (state) changes. It has a large ecosystem and is widely used in industry.
9.What is a component? Give examples from your project.
A component is a reusable piece of UI written as a function that returns JSX. Examples: FoodCard (one food item), Layout (header, navigation, footer), RequestRow (one request with Approve/Decline buttons), Modal, Badge.
10.What are hooks? Which hooks did you use?
Hooks let function components use React features. We used useState (form values, loading state), useEffect (side effects such as fetching data), useContext (sharing the logged-in user through AuthProvider) and custom hooks like useApi (fetch and auto-refresh data) and useDebounced (delay search until the user stops typing).
11.What is Tailwind CSS?
A utility-first CSS framework – we style elements with small classes like rounded-xl, bg-brand-600, md:grid-cols-3 directly in the markup. It keeps the design consistent and makes responsive layouts easy.
12.How did you make it mobile-responsive?
Using Tailwind breakpoints (sm:, md:, lg:), CSS grid/flex layouts that collapse to one column, and a hamburger menu on small screens. We tested at 375 px width (phone size) to ensure there is no horizontal scrolling.
13.How are pages protected so only logged-in users see them?
A Protected route component checks the user from AuthContext. If not logged in, it redirects to /login?next=…; if the role is wrong (e.g. a student opening “List food”) it redirects to the dashboard. The server also checks roles, so the frontend check is only for convenience.
14.How does the frontend talk to the backend?
Through a small api() helper using fetch. It sends JSON, attaches the JWT token in the Authorization: Bearer header, and throws a readable error if the server responds with an error. In development, Vite forwards /api calls to the backend on port 4000.
15.How do notifications update without refreshing?
Polling – the notification bell asks the server for new notifications every 20 seconds, and dashboards refresh their data every 15–30 seconds. In future this could be replaced with WebSockets for instant updates.
C. Backend
16.Which backend technology did you use and why?
Node.js with Express 5. Node lets us use TypeScript on both sides; Express is lightweight and makes it easy to define routes and middleware for a REST API.
17.What is a REST API?
A style of API where resources (listings, requests) are accessed with URLs and HTTP methods: GET to read, POST to create or perform an action, PATCH to update. Data is exchanged as JSON and each request is independent (stateless).
18.What is middleware?
A function that runs before the route handler. Ours: requireAuth (verifies the JWT), requireRole('PROVIDER') (checks the role), CORS, JSON body parsing and a central error handler that converts errors into proper HTTP responses.
19.Which HTTP status codes does your API use?
200 OK, 201 Created (new account, listing, request or upload), 400 Bad Request (invalid input, wrong pickup code), 401 Unauthorized (not logged in), 403 Forbidden (wrong role / not your listing), 404 Not Found, 500 Internal Server Error.
20.What is Zod and why did you use it?
Zod is a validation library. We define schemas (e.g. quantity must be an integer ≥ 1, deadline must be in the future) and every request body is checked before reaching the database, so bad data is rejected with a clear message.
21.How are images uploaded?
The browser sends the file as form data to POST /api/uploads. Multer receives it in memory, checks it is an image under 5 MB, and it is uploaded to Cloudinary (if API keys are set) or saved in the local uploads folder. The returned URL is stored with the listing. If no photo is added, a vegetarian placeholder for that food category is shown.
22.How does automatic expiry work?
The server runs a background job every 60 seconds (setInterval). It finds ACTIVE listings whose deadline has passed, marks them EXPIRED, marks their pending/approved requests as EXPIRED, and notifies the people involved. It also sends a reminder to approved users when less than 60 minutes are left.
D. Database
23.Which database did you use and why?
PostgreSQL, a relational database. Our data is naturally relational (users → listings → requests) and we need transactions to keep quantities correct. It is free, open-source and reliable.
24.What is an ORM? Why Prisma?
An ORM (Object-Relational Mapper) lets us work with database tables as objects in code instead of writing SQL. Prisma generates a type-safe client from our schema file, so a wrong field name is caught at compile time; it also creates the tables from the schema.
25.Explain your tables and relationships.
Four tables: User, FoodListing, FoodRequest, Notification. One provider (User) has many FoodListings (one-to-many); one FoodListing has many FoodRequests; each FoodRequest belongs to one requester (User); each Notification belongs to one User.
26.Why store both quantity and remaining?
quantity is the total originally listed; remaining is what can still be requested after approvals. Keeping remaining as a column lets us reserve stock atomically and show “36 of 40 left” instantly.
27.What is a transaction? Where did you use it?
A group of database operations that either all succeed or all fail (ACID). We use it when approving, rejecting, cancelling and collecting requests – e.g. reducing stock, changing request status and creating a notification happen together, so the data is never half-updated.
28.What are enums in your schema?
Fixed lists of allowed values: Role (PROVIDER, STUDENT, NGO), FoodCategory (MEALS, BAKERY, SNACKS, FRUITS_VEG, DAIRY, BEVERAGES, DESSERTS), Dietary (VEG, NON_VEG, VEGAN), ListingStatus and RequestStatus. The database rejects any other value.
29.Where does the sample data come from?
A seed script (prisma/seed.ts) creates demo providers, students and NGOs, about 90 listings and 350 requests over 8 weeks with realistic photos, so the charts and leaderboard have meaningful data. It is all demo data – no real personal data is used.
E. Security & authentication
30.How does login work?
The user sends email and password; the server finds the user and compares the password with the stored bcrypt hash. If correct, it returns a JWT containing the user id, role and name, signed with a secret key and valid for 7 days. The browser stores it and sends it with every request.
31.What is JWT? What are its parts?
JSON Web Token – a compact signed token with three parts: header (algorithm), payload (user id, role, expiry) and signature. The server can verify it without storing sessions, so it is stateless. If someone changes the payload, the signature no longer matches.
32.Why hash passwords? What is a salt?
Hashing is one-way, so even if the database leaks, real passwords are not revealed. A salt is random data added before hashing so identical passwords give different hashes, defeating pre-computed (rainbow table) attacks. bcrypt is also deliberately slow, which makes brute-forcing hard.
33.What is the difference between authentication and authorisation?
Authentication = proving who you are (login, JWT). Authorisation = what you are allowed to do (role checks – only providers approve; only the owner edits a listing).
34.Can a student approve their own request by calling the API directly?
No. The approve endpoint has requireRole('PROVIDER') and also checks that the listing belongs to that provider; otherwise it returns 403 Forbidden. Security is enforced on the server, not only in the UI.
35.How do you prevent SQL injection?
Prisma never concatenates user input into SQL – it uses parameterised queries. Inputs are also validated with Zod first.
F. Logic & algorithms
36.What happens if two requests are approved at the same moment and there isn’t enough food?
This is a race condition. We solve it with an atomic conditional update: “reduce remaining by q only where remaining ≥ q”. The database executes this as one step, so only one approval can succeed; the other gets “Not enough quantity left”. Remaining can never become negative.
37.What happens to pending requests when food runs out?
After an approval, any pending request asking for more than what remains is automatically declined and the requester is notified (“Only 2 servings remain – try a smaller request” or “fully claimed”).
38.Why a pickup code?
It proves the person collecting is the approved requester, prevents someone else taking the food, and ensures impact is counted only for food that was actually handed over. It is a random 4-digit number generated with Node’s crypto.randomInt.
39.Explain the request state machine.
PENDING → APPROVED → COLLECTED is the normal path. PENDING can become REJECTED or CANCELLED; APPROVED can become REJECTED (revoked), CANCELLED or EXPIRED, in which case its quantity is returned to the listing. Invalid jumps (e.g. collecting a rejected request) are refused.
40.How do search and filters work?
The Discover page sends query parameters (q, category, dietary, sort) to GET /api/listings. The server does a case-insensitive match on the title, description, pickup location and provider name, applies the filters, shows only active listings with food left, and sorts by deadline, newest or quantity. Typing is debounced so the server isn’t called on every key press.
41.How do you calculate CO₂ saved?
Food saved (kg) = Σ quantity × kg per unit for collected requests; CO₂e avoided = kg × 2.5, an average emission factor for wasted food based on FAO’s food wastage footprint estimates. It is an estimate, clearly labelled in the app.
42.How is the leaderboard ranked?
By kilograms of food rescued in the chosen period (week, 30 days, all time). Points are also shown: 10 × kg + 5 × pickups, rewarding both quantity and regular participation.
G. Testing, deployment & future
43.How did you test the project?
Manual end-to-end testing as each role in the browser (register, list, request, approve, wrong and correct pickup code, cancel, expiry), API testing with curl (role restrictions return 403, student limit, over-allocation), responsive testing at phone size, plus TypeScript type-checking and a production build.
44.What bugs did you find and fix?
Examples: a vegetarian listing without a photo showed a placeholder with meat (fixed with category-based vegetarian placeholders); new users were sent to the wrong page after sign-up; the provider’s listing order shuffled after updates (fixed with a stable sort); demo data expiring before a presentation (added a refresh command).
45.How would you deploy it?
Build the React app into static files and host on Vercel/Netlify; host the Express API on Render/Railway; use a managed PostgreSQL (e.g. Neon/Supabase); set environment variables (DATABASE_URL, JWT_SECRET, Cloudinary keys); enable HTTPS.
46.What are the limitations?
It is a prototype: notifications are in-app only (polling), there is no admin/moderator role, no automated test suite, food safety is the provider’s responsibility, and CO₂ uses an average factor rather than per-food values.
47.What is the future scope?
College login (SSO), SMS/e-mail/push notifications, real-time updates with WebSockets, maps to pickup points, AI demand prediction to reduce over-cooking, food-safety checklists, an admin panel, ratings/feedback, and Android/iOS apps.
48.How does the project support sustainability goals?
It reduces food waste and the greenhouse gases from it, helps food-insecure students and communities, and makes impact measurable – supporting UN SDG 2 (Zero Hunger) and SDG 12.3 (halve food waste).
49.What did you learn from this project?
Full-stack development with React and Node, relational database design, REST API design, authentication and role-based security, handling concurrency with transactions, building charts from aggregated data, responsive UI design, and testing from a real user’s perspective.
50.If the server restarts, is data lost?
No. All data is stored in PostgreSQL on disk; the server is stateless (it uses JWTs, not in-memory sessions), so after a restart users stay logged in and all listings and requests remain.
